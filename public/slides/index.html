    A ticket goes in.
    Software comes out.

    An order book simulator, built entirely by an AI agent responding to Jira tickets. Ten tickets, 114 tests, five modules, and no human wrote a line of it.

    These slides are hand-written. The application is not.

    What is a software factory?A production line where the raw material is a ticket

    In plain English: a status change in Jira wakes a robot. It reads the specification, reads the ticket, and decides whether it has been told enough to build the thing. If it hasn't, it says so and asks. If it has, it builds — and a person still decides whether it goes live.

    Before anything elseWhat this is not

    • Not autocomplete in someone's editor. A pipeline with gates, not a faster way to type.
    • Not autonomous. It cannot start work. It cannot ship without a person moving a ticket. It has no opinions about what is worth building.
    • Not silent. Every run ends with a comment on the ticket saying what it did, what it changed, and what it cost.

    Two boxes on the previous diagram are the whole talk — the agent judging the ticket, and the human gate. Everything else is plumbing.

    The claimThe bottleneck has moved

    It used to be building the thing.
    Now it is saying precisely what the thing should be.

    And to be clear about what that does not mean

    That is a claim about where the constraint sits, not about who is needed. Every module boundary, every correctness property and every definition of "done" in this application came from a person. What changes is where the day goes — less time on the fifth CRUD form, more on the decisions the typing used to squeeze out.

    Engineering moves up the stack, not out of the building.

    The rest of this talk, in one lineWriting requirements an AI can follow is just… writing good requirements

    The discipline we all already know we should apply, and mostly don't — because we can rely on an experienced person at the other end quietly filling in what we left out.

    There is nothing here you have not been told before.

    The only new thing is that vagueness now has a price and a timestamp on it. It fails in four minutes instead of six weeks, and it fails in front of you.

    The PRDEverything here was built from one document

    Every requirement has a number. A ticket does not describe what it wants — it cites it.

    That difference is most of the reliability. A description is an invitation to interpret; a citation points at a fixed definition that two people, or an agent, can both read.

    In plain English: what costs money is not typing, it is thinking. On one ticket, 45% of the model's output was reasoning rather than code. Which means a vague ticket is not only riskier, it is more expensive: the agent has to reason its way to a decision the ticket should have made.

    The slide to saveSix things that made that ticket work

    • Concrete criteria, not abstract ones. Numbers, not adjectives.
    • Criteria that read as test names. They became the 22 tests almost verbatim, so the tests can be read against the ticket line by line.
    • A citation, not a description. "Implements REQ-1..REQ-4."
    • An explicit out-of-scope list. Without one, a helpful agent gold-plates.
    • A stated visual expectation — here, deliberately none. Saying so stops it inventing something to show.
    • Named constraints. The boundaries it must not cross.

    Where my instinct was wrongSize the ticket to the interface, not to the effort

    My instinct was lots of small tickets — the way you would break work down for a team. Slice the engine into "add limit orders", then "add market orders", then "add cancellations".

    The second agent inherits whatever shape the first invented, and it cannot ask the first one anything — that conversation is over and the context is gone. One design decision becomes a negotiation between two robots who cannot talk to each other.

    The real question is not "is this too big"

    It is do the acceptance criteria fully constrain the outcome? A vague small ticket is no safer than a vague big one. Split when a ticket spans modules — separate interfaces, separate owners. Which is, on reflection, exactly how you would hand work to people.

    Another example of where I messed upThe ticket was wrong

    It claimed a bid of 99 against an ask of 101 gives 100 basis points — and quoted the formula that gives 200.

    There are two ways to quote a spread in basis points, and both are used. The quoted spread uses the whole gap; the half-spread uses the distance from the middle to one side. They differ by a factor of two, and my ticket had one number with the other one's formula.

    I wrote it. I reviewed it. I seeded it onto the board. Nobody caught it.

    The agent caught it. It refused to build, and named the exact ambiguity.

    Same ticket, a cheaper modelIt found the contradiction — then worked around it

    In plain English: this is the model thinking out loud, and it committed the thinking into the test file.

    // bps = (ask - bid) / mid * 10000
// So: (101 - 99) / 100 * 10000 = 200
// Let me re-read: "spread divided by mid, times 10000"
// Oh! I think I misread. Let me re-read the ticket...
// Yes! That's it! The formula is probably: ((ask - bid) / 2) / mid * 10000

    It shipped a formula reverse-engineered to produce my wrong number. All tests passed. It reported success.

    This is the failure mode to be frightened of. Not a crash. Not a red test. A green build of the wrong requirement, reported confidently — and a reviewer skimming a green tick would have approved it.

    The fair challenge"So you fixed it by buying a bigger model. That is not a fix."

    Correct. A better model shifts the odds. It does not remove the failure class. Anyone who tells you a model choice makes this safe is selling something.

    So do not defend at the model. Defend where it does not matter what the model thought the ticket meant:

    1 · Invariants

    Rules that must hold for every input, written by a person, from the domain, before the ticket existed. The wrong build passed every test it wrote — because it wrote them from its own misreading. No interpretation survives a rule it did not author.

    2 · The human gate

    The number was on screen, in a preview, before anything shipped. A person looking at a rendered figure is a genuinely different kind of check from any test.

    3 · An adversarial reviewer

    A second agent whose only job is to attack the change. We have not built it. This is the strongest argument for it.

    And the honest residual

    A wrong requirement that no invariant covers and no reviewer notices. We have that hole today. Hand the same ticket to a capable contractor in week one and you get the same outcome, slower and dearer. What is new is the throughput — which is why the rails have to scale with it.

    Let's dig in a bitBehind the curtain

    • CLAUDE.md — the house rules, read at the start of every run. Synthetic data only. No dependencies. Never commit to main.
    • build-prompt.md — the agent's job description, kept outside the workflow so it can change without a merge.
    • jira.sh — how the robot talks to Jira. Reads, comments, moves statuses, and @-mentions a real person when it needs an answer.
    • The guardrails: it only commits to its own branch; the deploy agent refuses to merge anything with a failing check; and a silent run is a failed run.

    One honest note: there is no required-reviewer rule on main, because the agent doing the merge would be blocked by it. The gate is real — it just lives in Jira instead of GitHub. If you copy this, know that is the trade.

    The objection I will make for youThe agent wrote the code and the tests

    So the tests confirm what it decided to build — not what we asked for.

    A misunderstanding gets written down twice, and the suite goes green.

    That has a name: the self-validation problem. And AI is unusually good at making wrong answers look right.

    Defence oneTests come first — and we make it provable

    "The agent says it wrote the tests first" is an assertion. So instead:

    ✕  commit 1  Add tests for LLD-14 (spread in basis points)
    ✓  commit 2  Implement basis-point spread

    The tests are committed on their own and pushed. CI runs and goes red. The implementation lands as a second commit and CI goes green.

    The commit list is the evidence. A test that existed before the code cannot have been shaped by it.

    The limit: this is temporal separation, not agent separation. The same model still wrote both, in one sitting.

    Defence twoSix rules that must hold for every possible input

    In plain English: an acceptance criterion checks one example. An invariant is a rule we throw thousands of random orders at, and check after every single operation.

    • The book never crosses. The best bid is always below the best ask.
    • Volume is conserved. Matching creates and destroys nothing.
    • Price–time priority is respected. Among orders at the same price, the earliest fills first.
    • No trade-through. Liquidity is always consumed best-price-first.
    • The book is well-formed. Nothing zero-sized rests; nothing filled remains reachable.
    • Queue integrity. Positions run from 1 with no gaps, and removing an order closes the gap behind it.

    These are numbered in the specification as INV-1…INV-6, so a ticket can cite them and the agent must satisfy them. They are the real correctness properties of an order book — not proxies for them.

    Invariants aren't new — they're our data quality testsWe already have a team whose job is writing exactly these

    Invariants are not a technique I found in a blog post. The content team writes data-quality invariants for a living, and engineering builds them into our parsers.

    That discipline is what makes generated code safe to trust.

    The factory is only as trustworthy as the invariants guarding it.

    The content team's existing discipline becomes the safety rail, and the rail scales with the automation instead of lagging it.

    Being straight about itWhat this proves, and what it doesn't

    Proves

    • A well-specified ticket becomes tested, previewable, deployed software with no human writing code.
    • An agent will decline work it cannot responsibly do.
    • A whole small application can be built this way, from a specification.

    Does not prove

    • That we can point this at our large, complex, long-lived systems tomorrow.
    • This is a small application with nothing at stake, built from a specification that did not exist until it was written for the purpose.

    Total cost of everything you have seen: $38.78 — including two failed runs.

    Four things have to be true firstAnd note the order

    PrerequisiteWhy
    A staging environmentThis deploys straight to production because nothing is at stake. Anything real cannot.
    A real test suiteThe agent is only as safe as what it can run.
    A risk tier for changesA label change and a change to business logic must not travel the same path.
    A written specificationWhat you specify is what you get. There is no way around this one.

    The first three are engineering work. The fourth is the one that actually gates everything — and it is product work.

    Over to you — this is the gate your ticket has to passThe Definition of Ready

    The agent builds it only if all four are true:

    1 · A clear outcome

    What can a user do afterwards that they cannot now?

    2 · At least one acceptance criterion you could write as a test

    If you cannot imagine the test, neither can it.

    3 · You can tell what should look different on screen

    Even if the answer is "nothing" — say so.

    4 · It does not break a hard rule

    No real data. No dependencies. Never commit to main.

    The skill that mattered was not engineering.

    It was writing down precisely what we wanted — which is a thing this organisation already does, in every ticket, every day.

    The difference is that now the vagueness costs you immediately and visibly, instead of six weeks later.
